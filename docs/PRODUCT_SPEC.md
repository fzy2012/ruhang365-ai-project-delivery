# 产品规格：AI 全流程项目共创与交付框架

## 1. 产品定义

面向没有代码基础或不希望承担技术判断的项目负责人，提供从目标澄清到交付验收的 AI 协作框架。产品不是通用开发规范集合，而是一个根据任务复杂度自动收缩、根据风险自动增强的项目交付编排器。

## 2. 用户与问题

### 目标用户

- 有业务目标但没有代码基础的个人或小团队；
- 能判断结果是否有价值，但无法可靠选择技术栈和架构的人；
- 希望使用 AI 完成产品、自动化、内部工具或现有系统改造的人。

### 核心问题

- 用户不知道是否需要自研；
- AI 容易把技术选择转嫁给用户；
- 需求、方案、开发和验收之间缺少稳定闸门；
- “代码写完”经常被误报为“项目完成”；
- 部署、维护、恢复和交接在最后才暴露。

## 3. 产品目标

1. 让用户只承担能以业务后果判断的决定。
2. 在开发前选择成本、风险和控制力合理的交付方式。
3. 为不同复杂度任务使用不同深度，避免流程过重或风险失控。
4. 把验收标准变成实施前的共同基线。
5. 用真实运行证据完成交付，而不是以代码或口头结论代替。
6. 相比同环境、不使用本 Skill 的 Codex，在同等质量和同一交付目标下，总成本增量不得超过 10%，优先做到持平或下降。10% 是验收上限，不是计划消耗的额度，也不因声称质量更好而自动放宽；当前尚未证明达标。

用户体验：用户只描述目标，由 AI 自动匹配和推进。进度或决定实质变化时，简明说明当前目标、正在做什么、需要用户决定什么及下一步；无变化或不适用的项省略。Light / Full / High assurance 只在内部使用，除非用户主动询问。

实施任务的交付终点：用户有可进入的位置或启动方式，能执行核心动作并获得约定结果；AI 已验证真实路径及相关失败情形。分析或方案请求仍以其约定范围为准。实际用户验收单独记录，未由用户使用或确认时不得以 AI 检查代替。

## 4. 非目标

- 不替代具体的前端、后端、移动端、部署或平台 Skill；
- 不建设通用自主开发 Agent Runtime；
- 不默认托管用户代码、数据或凭据；
- 不保证项目一定成功、盈利、上线或获得用户；
- 不为简单任务制造强制三方案和长篇文档。

## 5. 核心对象

```text
Goal
→ Delivery Mode
→ Delivery Path
→ Decision
→ Acceptance Baseline
→ Milestone
→ Evidence
→ Delivery Card
```

- `Goal`：用户要解决的问题、目标用户和业务结果。
- `Delivery Mode`：轻量、完整或高保障。
- `Delivery Path`：买、配、连、改、建中的一个或组合。
- `Decision`：会影响范围、成本、体验、风险或长期维护的用户决定。
- `Acceptance Baseline`：用户可观察结果与 AI 工程验证要求。
- `Milestone`：可运行、可观察、不依赖大量占位的阶段结果。
- `Evidence`：命令、测试、浏览器、接口、部署或用户验证证据。
- `Delivery Card`：访问、使用、维护、恢复和交接信息。

## 6. 复杂度路由

| 模式 | 适用条件 | 最小流程 |
|---|---|---|
| 轻量 | 范围清楚、低风险、可逆、无架构决定 | 目标复述 → 简要验收 → 实施 → 验证 |
| 完整 | 新项目、中等功能、存在多种合理路径 | 预检 → 路径比较 → 决策 → 双层验收 → 里程碑 → 交付 |
| 高保障 | 已确认的生产变更、支付处理、敏感数据、合规、特权访问、迁移或不可逆风险 | 完整模式 + 相关风险、恢复方式和实际动作所需确认；普通内部角色或审批本身不升级 |

## 7. 买、配、连、改、建

| 路径 | 含义 | 优先考虑条件 |
|---|---|---|
| 买 | 直接使用成熟产品 | 通用需求、时间优先、可接受订阅和平台边界 |
| 配 | 配置现有产品或插件 | 核心能力已有，只需规则、表单、权限或视图 |
| 连 | 连接多个现有系统 | 价值来自数据流和自动化，而不是新产品本身 |
| 改 | 在现有项目局部开发 | 已有用户、数据、契约或基础设施需要保留 |
| 建 | 从零自研 | 差异化、控制权或长期价值足以覆盖开发维护成本 |

不得为了满足方案数量制造伪方案；存在一个合理路径时，直接推荐一个。

## 8. 决策与授权闸门

1. 方案闸门：影响成本、体验、数据、安全、锁定或维护时由用户确认。
2. 验收闸门：完整模式下，实施前明确用户验收目标；已有确认继续有效，仅在重要业务取舍尚未决定时询问，不因阶段变化重复确认。
3. 实施闸门：计划模式、只读请求或用户明确说先不动时，不写文件。
4. 高风险闸门：付费、生产、真实数据、域名、权限、发布和不可逆操作单独确认。

“继续”只推进当前已授权范围，不自动授权推送、发布、部署、付费或扩大范围。

## 9. 双层验收

- 用户验收：使用可观察的行为、结果和失败反馈描述。
- 工程验收：由 AI 选择适用的构建、类型、测试、安全、性能、错误和回退验证。

状态只使用 `PASS`、`FAIL`、`BLOCKED`、`N/A`。没有真实证据不得标记 `PASS`。

## 10. V1 交付面

- 一个可安装的 Codex Skill；
- 三个按需加载的参考模板；
- 三类冻结评测案例；
- 一套静态合同验证；
- 一份入行实验室接入合同。
